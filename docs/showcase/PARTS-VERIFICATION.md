# 三部件卡车：真实验证记录

日期：2026-10-13。本轮交付：部件标记、通道预览、外观参考绑定、完整拍摄包及恢复。没有调用下游视频生成服务，生成模型是否服从遮罩需要单独测试。

## 实际案例

一台原创卡车分为车头、车厢、车轮三个部件，共15个网格；配置2秒前侧运镜和一个清晰侧面机位。前景路灯用于检查真实遮挡。先在真实Chrome界面读取网格、保存车头标记与名称，再上传并绑定一张AI生成外观图。图片描述红色车头、银灰金属车厢与黑色橡胶；只用于外观，不要求改动白模三轴结构。

真实Codex CLI通过MCP读取工程与15个实际网格，用一次原子事务新增车厢、车轮两个用途记录并绑定，补充三个部件约束说明。三条用途记录复用同一份原始图片哈希。模型调用了彩色Part ID和三个黑白遮罩的真实图像预览，再回读工程。独立对比before/after证实：对象身份、布局、颜色、模型选择、部件网格与所有镜头一致；只有授权的参考绑定、记录及部件备注改变，revision 4→5。

## 拍摄包

通过真实界面选择三个部件，并启用深度/对象ID，启动正式导出。完成后下载原ZIP并独立校验：

| 项目 | 实测结果 |
| --- | --- |
| RGB视频 | 1280×720、24fps、48帧、2秒，H.264 |
| Part ID | 48张无损PNG，精确整数映射 |
| 黑白遮罩 | 三部件各48张，共144张 |
| 其他控制 | 48张深度、48张对象ID；与同一镜头时间对齐 |
| 外观 | 3条用途记录、1份原始图片字节，保留部件绑定与备注 |
| 清单 | 297项文件大小/SHA-256核验；另含manifest本身 |
| 结构检查 | 每帧、每部件的白像素集合恰好等于Part ID对应像素，遮挡保留 |
| 媒体检查 | FFprobe实际解码；浏览器完整播放到ended=true、currentTime=duration=2秒，无媒体错误 |

把ZIP里的原始图片通过公开资产接口恢复到另一个全新工作空间，再导入完整工程。核对部件、网格选择、绑定、全部镜头及图片用途记录逐项一致；远端本地资产接口读回的原始图片SHA-256一致。GUI的ZIP恢复流程另由真实浏览器E2E覆盖缺文件、错哈希和完整恢复。本次手工确认遇到浏览器焦点切换，未将取消的手工导入尝试称为成功；实际案例恢复采用正式资产/API路径，随后在导演台查看恢复结果。

## 回归范围与修复

`npm run check`通过96项结构、真实HTTP、MCP/CLI、图片解码及拍摄包校验测试，同时通过格式、schema同步、作者资产和构建检查；浏览器完整套件18个流程通过，包括3个新的编辑/恢复流程与3个精确通道流程。精确渲染测试覆盖：

- 三个部件的原始RGB ID与各自黑白遮罩逐像素对应。
- 前景物体遮住部件时白区域减少，允许完全遮挡，不补全轮廓。
- 改变展示颜色、对象顺序或增加非部件对象，不改变对应ID画面。
- 随机跳转时间、穿插高亮/ID/遮罩后，普通RGB帧逐字节恢复。
- 真实自包含GLB中重复节点名称不影响子索引选择；错误路径明确拒绝。
- 错误网格、缺失图像、损坏图片、MIME错配、重复遮罩选择、过期写入均不会提交。

修复了删除当前部件时预览选择可能滞后的竞态；遮罩中隐藏了编辑控件；增加了部件约束说明、节点编辑收起与参考图命名。输入图片实际解码后再保存，ZIP恢复会先核对参考图内容哈希。

Chrome界面的错误日志未发现应用错误；可见警告来自用户既有浏览器扩展的内容脚本。移动端基础布局在原有回归中检查，新模块精细交互主要验证桌面Chrome。

## 证据和边界

原始媒体、参考图、ZIP、主/恢复工作空间、逐项核验JSON及真实Codex事件留在被Git忽略的 `.hengdian/parts-case`、`.hengdian/parts-restore` 与 `.hengdian/parts-codex`。仓库包含精选真实截图和不带缺失图片引用的 [可编辑案例](../../examples/truck-parts/README.md)。它们是本地证据，不是远程备份声明。

当前输出是可见不透明表面的控制信息；没有透明覆盖、运动模糊/景深覆盖、Cryptomatte EXR、自动面片分割或跨对象控制组。Part ID与外观图可以完整交接，不等于任意生成模型都能锁定结构、解决部件粘连或产生自然动作。
